# 近期开发任务卡片

更新时间：2026-04-24
适用范围：当前 `main` 分支
用途：把最新项目评估收敛成可直接执行、可交接、可验证的任务卡片

## 1. 使用规则

- 本文件是当前阶段的执行基线，优先级高于旧卡片标题和口头同步。
- 任务状态变化后，至少同步更新：
  - [现状评估](./01-现状评估.md)
  - [后续路线图](./02-后续路线图.md)
  - [未来两周开发排期](./04-未来两周开发排期.md)
- 如果任务被拆分，必须补充“本轮只做哪一层、下一层留给谁”。
- 如果任务直接影响协作者接线，也要同步更新 [协作任务清单](./03-协作任务清单.md)。

## 2. 任务卡片

### 卡片 C1：清理前端测试环境污染

- 优先级：
  - `P0`
- 建议负责人：
  - 主开发线
- 任务目标：
  - 让 Vitest 不再把 `.review/`、额外 worktree 和临时副本当作当前仓库测试一起执行。
- 建议修改范围：
  - `vitest.config.ts`
  - `package.json`
  - `docs/项目文档/04-质量与发布/01-测试与验证.md`
  - 必要时最小更新 `docs/项目文档/01-总览/02-运行与开发.md`
- 交接目标：
  - `npm run test:web-core` 和 `npm run test -- --run ...` 只命中当前仓库测试文件
  - 测试输出不再出现 `.review/` 路径
  - 文档明确说明本地 review worktree 的处理方式
- 禁止红线：
  - 不直接删除现有 `.review/` 工作树
  - 不重做整套前端测试框架
  - 不为了“看起来干净”而降低现有测试覆盖
- 最小验证：
  - `npm run test:web-core`
  - `npm run test -- --run src/platform/webRuntime.test.ts src/stores/__tests__/gameStore.test.ts src/components/__tests__/AgentTracePanel.test.ts src/components/__tests__/NoNameDebugConsole.test.ts`
- 作用效果：
  - 恢复前端测试结果的可信度
  - 降低 review / 本地开发 / CI 三者之间的验证偏差
  - 让后续 NoName UI 与 Web mock 调整更容易判断真假回归

当前状态：

- 第一轮已完成
- `vitest.config.ts` 已把前端测试发现范围收紧到 `src/`，并显式排除 `.review/`
- `npm run test:web-core` 已恢复只命中当前仓库测试
- NoName 前端定向测试已恢复只命中 `src/` 下的 4 个目标文件
- `docs/项目文档/04-质量与发布/01-测试与验证.md` 与 `docs/项目文档/01-总览/02-运行与开发.md` 已同步更新

### 卡片 C2：修复章节压缩对 compaction summary 的回吃风险

- 优先级：
  - `P0`
- 建议负责人：
  - 协作者优先，主开发线审合并
- 任务目标：
  - 避免章节 compaction 在重复执行时，把之前写回的 compaction summary 再次当作 structured note 输入，形成递归沉淀。
- 建议修改范围：
  - `src-tauri/src/noname_memory_manager.rs`
  - 必要时最小改动 `src-tauri/src/noname_memory_compaction.rs`
  - 对应测试文件
- 交接目标：
  - `build_chapter_compaction_input` 能稳定排除不应重复沉淀的 summary 型 note
  - 至少新增 1 个回归测试，覆盖“先写回 summary，再重复 compact 同章”的场景
  - 保持 active / resolved / archived 的既有边界不被破坏
- 禁止红线：
  - 不借机重写整套 compaction 结构
  - 不在本任务里顺手接入 runtime 章节推进主链
  - 不扩大 notes 的自动写回范围
- 最小验证：
  - `cargo test noname_memory_manager -- --nocapture`
  - `cargo test noname_memory_compaction -- --nocapture`
- 作用效果：
  - 解除当前 chapter compaction 合并阻塞
  - 防止章节摘要被重复压缩后逐轮失真
  - 为后续 notes 与章节收束接线提供可靠输入边界

当前状态：

- 第一轮已完成
- `NoNameMemoryManager` 已新增 `build_chapter_compaction_input` 与 `compact_chapter_from_memory`，集中承接章节压缩输入构造
- 章节压缩输入现已只消费当前章节的 episodic events，以及非 `archived`、非 `compact-chapter-*` summary 的 narrative notes
- 已补充“按章节筛选 episodic memory”与“先写回 summary，再重复 compact 同章”两类回归测试
- 当前已确认旧的 chapter summary 不会在后续重复压缩时被再次回吃；后续重点转向 `C3`，明确章节收束的调用顺序

### 卡片 C3：明确章节收束时 notes 与 compaction 的调用顺序

- 优先级：
  - `P1`
- 建议负责人：
  - 主开发线
- 任务目标：
  - 收敛“章节收束时先 compact、先 archive、还是先写回 summary”的顺序，避免 notes 生命周期和 compaction 结果打架。
- 建议修改范围：
  - `src-tauri/src/noname_memory_manager.rs`
  - 必要时最小改动 `src-tauri/src/noname_runtime.rs`
  - `docs/项目文档/02-架构/02-NoName-代理系统.md`
  - `docs/项目文档/03-规划/01-现状评估.md`
  - `docs/项目文档/03-规划/02-后续路线图.md`
- 交接目标：
  - 形成一条明确的章节收束顺序说明
  - 如果落代码，只新增最小 orchestration helper，不直接扩张 runtime 复杂度
  - 文档能说明“何时 compact、何时 archive、何时 upsert summary”
- 禁止红线：
  - 不跳过人工 review / second guardrail 体系去碰最终剧情状态
  - 不把大段章节收束逻辑重新堆回 `tauri_commands.rs`
  - 不在没有顺序说明的情况下直接接入正式章节推进流程
- 最小验证：
  - `cargo test noname_memory_manager -- --nocapture`
  - `cargo test noname_runtime -- --nocapture`
  - 文档自查，无失效引用
- 作用效果：
  - 让 structured notes、compaction summary 和章节归档形成稳定顺序
  - 降低后续章节推进接线时的重复设计成本
  - 避免“功能都在，但调用顺序不稳定”导致的隐性回归

当前状态：

- 第一轮已完成
- `NoNameMemoryManager` 已新增 `close_chapter_memory`，把章节收束顺序固定为“先 compact，再 organize/archive resolved notes，最后 upsert chapter summary”
- 当前顺序约束已经补入回归测试：resolved notes 会进入本次章节摘要，但本次 note review 不会把新写回的 summary 误记为 carried-forward active note
- 本轮未把章节收束 helper 直接接入正式 runtime 章节推进流程；后续如要接线，应复用该 helper，而不是重新拼装顺序
