# 实现计划（V3）: Nobody 前端/UI 全面重构

## 1. 我对项目现状的理解

基于 `tasks.md`、`tasks_v2.md` 与当前前端代码，Nobody 已从“可玩原型”演进到“规则引擎 + LLM 增强”的复杂系统，后端能力已明显超前于前端呈现。  
当前前端已经覆盖主要功能（剧本选择、游戏推进、信息面板、导出、设置等），但存在典型的“功能堆叠后 UI/交互债务”：

1. 页面信息密度过高，核心阅读路径（剧情 -> 决策 -> 反馈）被大量工具按钮分散。
2. `GameView.vue` 职责过重，视图、状态编排、交互控制、快捷键、自动推进耦合在一起，维护成本高。
3. 面板体系分裂（顶部工具栏 + 多弹窗 + 信息面板 Tab），用户心理模型不稳定。
4. 视觉语言不完全统一（按钮语义、色彩语义、动效语义不一致）。
5. 存在文本编码异常（中文乱码）与术语不统一，影响沉浸与专业感。
6. 可访问性与可观测性有基础，但未形成标准化体系。

V3 目标不是“再加组件”，而是建立一套可持续演进的前端架构和视觉系统。

## 2. V3 总体目标

### 2.1 体验目标

1. 让玩家持续聚焦“读剧情 + 做选择 + 看结果”主循环。
2. 让复杂系统能力（地图、关系、战斗解释、一致性诊断）变成“按需可见”，而不是“默认噪音”。
3. 在长时游玩（30+ 回合）下，阅读疲劳显著下降，操作路径稳定。

### 2.2 工程目标

1. 将前端从“页面中心”重构为“域模型 + 组件编排 + 设计令牌”架构。
2. 拆分超大组件，降低耦合，提高单测与回归效率。
3. 建立统一 UI 规范（颜色、间距、层级、动效、状态反馈、文案规范）。

### 2.3 量化验收指标

1. 核心交互（继续推进/提交输入/选项选择）响应反馈 < 150ms（本地前端侧）。
2. `GameView` 主文件行数降至可控范围（建议 < 450 行，按域拆分）。
3. 新 UI 下可用性走查任务成功率 >= 90%（至少 10 条任务）。
4. 前端关键路径单测/组件测试通过率 100%，无 P0/P1 视觉回归。

## 3. 视觉与交互设计方向（V3）

### 3.1 视觉主题: 「玄卷墨金」

1. 主基调：深墨青黑 + 温金强调 + 冷青辅助，保持修仙气质与可读性平衡。
2. 字体分层：
   - 标题：衬线风格（章节感、仪式感）
   - 正文：高可读中文正文字体（长阅读优先）
   - 数据：等宽/半等宽（状态与日志清晰）
3. 背景层次：低对比渐变 + 微纹理，避免纯平背景疲劳。
4. 动效策略：只保留“章节切换、状态切换、面板开合”三类关键动效，避免噪声动画。

### 3.2 信息架构（IA）重排

V3 采用“三层视图”：

1. `主舞台层`（默认视图）
   - 左中：剧情阅读区（主焦点）
   - 底部：交互输入区（选项/自由输入/继续推进）
   - 右侧：精简状态卡（角色、章节、当前位置）
2. `世界层`（侧栏/抽屉）
   - 地图行程、关系网络、战斗复盘、章节目录
3. `系统层`（设置与诊断）
   - LLM 设置、一致性策略、调试上下文、错误中心

原则：高频内容常驻，低频内容抽屉化。

## 4. 前端重构策略

### 4.1 组件分层

1. `views/`：页面编排层（只做布局与路由级状态组装）。
2. `features/`：按领域切分（story、input、map、character、diagnostics、export）。
3. `shared/ui/`：基础组件库（Button、Panel、Dialog、Tabs、Badge、Toast、EmptyState）。
4. `shared/theme/`：设计令牌（色彩、字体、半径、阴影、动效、z-index）。

### 4.2 状态管理治理

1. `gameStore` 继续做“单一事实源”，但拆分派生逻辑到 `composables`。
2. 新增：
   - `useStoryFlow()`：交互状态机（waiting/auto/cooldown/loading）
   - `useInputMode()`：输入模式与校验
   - `useUiPanels()`：面板开合与快捷键集中管理
3. 清理页面内“跨职责 watch/watchEffect”堆叠，减少隐式副作用。

### 4.3 文案与编码治理

1. 修复全部中文乱码与异常编码。
2. 建立术语表：境界、灵根、战斗解释、章节、一致性风险分等统一表达。
3. 错误提示分级：`阻断错误`、`可恢复错误`、`提示信息`。

## 6. 核心页面改版方案（目标态）

### 6.1 主菜单 `MainMenu`

1. 保留单屏聚焦，增加“最近存档继续”卡片。
2. 一级入口只保留：新游戏、继续、设置、退出。
3. 音频控制移入设置抽屉，避免主菜单信息过载。

### 6.2 剧本选择 `ScriptSelector`

1. 改为两列：左侧剧本类型卡，右侧参数配置（主角名、导入设置、提示）。
2. 不同剧本流程显示明确步骤（选择文件 -> 解析 -> 角色确认 -> 开始）。
3. 加载反馈统一为阶段进度条 + 可恢复提示。

### 6.3 游戏主界面 `GameView`

1. 顶栏减重：只保留高频动作（返回主菜单、保存、设置入口、信息抽屉开关）。
2. 阅读区优先：章节、正文、上一章摘要、滚动定位器。
3. 交互区统一：输入模式切换、选项按钮、自由输入、继续推进共用视觉框架。
4. 右侧状态卡常驻：角色、章节、地点、系统状态（不再依赖多弹窗来回切）。

## 7. 风险与规避

1. 风险：重构期 UI 改动大，容易引入回归。
   - 规避：阶段化替换 + 每阶段快照测试 + 冒烟脚本。
2. 风险：样式重构导致开发节奏下降。
   - 规避：先落主题令牌与基础组件，再迁移业务组件。
3. 风险：复杂交互（自动推进 + 弹窗 + 快捷键）冲突。
   - 规避：统一收敛到 `useUiPanels` 与 `useStoryFlow`。

## 8. 开发执行约定（本终端）

1. 以 `tasks_v3.md` 为前端/UI 改造唯一任务基线。
2. 每完成一个核心阶段（A/B/C/D/E/F/G）即提交一次 Git，提交信息使用中文。
3. 优先保证可运行与可回归，再做视觉细节打磨。
4. 若发现与现有未提交改动冲突，先隔离改造范围，避免覆盖他人/历史改动。
